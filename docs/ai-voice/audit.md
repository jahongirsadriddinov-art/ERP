# Code audit (2026-10-12)

## auth-rbac-models

AUTH/JWT: Login paths are POST /api/auth/send-otp + /verify-otp (SMS via Eskiz), /send-code + /login (4-digit Telegram code stored in plaintext in User.telegramVerificationCode, compared with !== at backend/src/routes/auth.ts:374), /telegram-webapp (HMAC-verified Telegram Mini App initData, auth.ts:399-439), /dev-login (password + 2FA, 365d token, auth.ts:441-530), and QR login (routes/qrlogin.ts /create, /code/:id, /scan, /approve, /finalize). They all end in issueSession() (auth.ts:35), which checks isBlocked and the latest Subscription (pending/expired/rejected gives 403). It then calls services/sessions.ts issueTokenWithSession(), which creates a Session doc {userId, jti, deviceLabel, ip, loginMethod, revoked, lastSeenAt}, sends a Telegram "new device" alert and signs an HS256 JWT {userId, role, companyId, branchId, isOwner, isDeveloper?, jti}, valid 7d by default. JWT_SECRET falls back to the literal 'secret' if the env var is missing (middleware/auth.ts:44). requireAuth (auth.ts:155) verifies the token, then loadFreshUser() (auth.ts:120) re-reads role/companyId/isOwner/isBlocked from the DB on every request, so the token's claims are not trusted. isDeveloper is derived as role==='dasturchi'. requireAuth then checks Session.revoked by jti (tokens without a jti skip this), the site/app maintenance flags (AppSettings, 5s cache), and the workGate, and finally calls runWithTenant(ctx, next). optionalAuth (auth.ts:209) does the same but continues as a guest on failure. Helpers: requireOwnerOrAdmin (isDeveloper|isOwner|direktor|orinbosar), requireDeveloper, blockDeveloper (stops dasturchi from reaching firm-internal routes). Sessions API (routes/sessions.ts, mounted at /api/sessions): GET /, DELETE /all, DELETE /:id, which set revoked=true and call socket kickSession(jti). Session TTL index is 366d.

TENANT CONTEXT: middleware/tenantContext.ts keeps an AsyncLocalStorage<TenantContext{userId, role, companyId, isOwner, branchId, isDeveloper}> with getTenant(), currentCompanyId() and runWithTenant(). There is NO Mongoose tenant plugin or global hook. Isolation is manual and per query, through middleware/scope.ts: scoped(filter) adds {companyId: cid}. It adds no filter for a developer, adds companyId:null for an authenticated user without a company (legacy pool), and adds no filter at all when there is no context (unauthenticated/optionalAuth). stamped(doc) sets companyId from the context, never from the body. companyId is stored as a String on every model, not an ObjectId ref. The Telegram bot (services/bot.ts) runs OUTSIDE any tenant context: it finds the user by User.findOne({telegramChatId}) and passes companyId explicitly (e.g. bot.ts:802).

WORK GATE (middleware/workGate.ts): WORKER_ROLES=['ishchi','prorab','brigadir']. isOnShift(userId) reads today's Attendance (todayInTashkent), with a 20s in-memory cache, and checks checkIn && !checkOut. workGateBlocks() returns HTTP 423 {checkinRequired:true} for every path except /api/attendance, auth, gps, pin, sessions, push, errors, status, currency, and GET /api/users, /api/company, /api/notifications/unread-count. invalidateShift() clears the cache.

FEATURE GATE (middleware/requireFeature.ts): requireFeature(key) reads the latest Subscription for the company and uses subscriptionFeatures() (the plan features from config/plans.ts getPlanInfo, or customFeatures for the 'custom' plan). It returns 403 {featureRequired} only when a plan is found and lacks the key; it fails open for a missing plan, a missing companyId or a DB error. companyHasFeature(key) is the boolean version (fails closed). Used keys: ai_assistant (routes/ai.ts), audit_log, backup, multi_currency, gps_tracking, qr_tools, income (checked inline in transactions.ts).

ROLES: User.role enum (models/User.ts:53) = direktor, orinbosar, ishchi, prorab, brigadir, dasturchi (super-admin). There are no other roles (no hisobchi/omborchi/mijoz) in the frontend or backend. User.isOwner is a separate flag. There is no central permission matrix. Each route does ad-hoc inline checks such as tenant.role==='direktor'||'orinbosar' ("isBoss") in attendance.ts:49/102/253, gps.ts:128/159/195, objects.ts:409/429, documents.ts:107, transactions.ts:50/149/380/479/576, users.ts:58/112/158/208, audit.ts:16, dashboard.ts:17, backup.ts:25, safety.ts:74, and signDocs.ts:24 (adds prorab). The bot has isAdmin/isDev/isWorker helpers (bot.ts:693-696). AI routes use a local requireBoss (routes/ai.ts:66: isOwner, or DB role direktor/orinbosar) + requireFeature('ai_assistant') + an in-memory rate limit (aiLimit). The AI chat currently uses Groq (GROQ_API_KEY/GROQ_MODEL, JSON-mode chat). Gemini is used only for audio/receipt parsing (services/gemini.ts geminiAudioToJson, services/botExpense.ts voiceToExpense/receiptToExpense).

ROUTE MOUNTING (backend/src/index.ts:234-307): requireAuth+blockDeveloper on objects, transactions, materials, smeta, ai, attendance, gps, equipment, safety, documents, payroll, export1c, announcements, sign-docs, dashboard. requireAuth only on users, messages, groups, companies, company, audit-logs, search, qr, notifications, calls, geocode, admin. optionalAuth on auth, push, currency, errors. Public: register, files, status, public (client portal by token), deploy, payments.

### Bugs / risks
- **backend/src/services/bot.ts:2853 notifyAdmins(), called from backend/src/routes/transactions.ts:245** [high] Cross-tenant data leak: User.find({role:{$in:['direktor','orinbosar']}, telegramChatId exists}) has no companyId filter. Every new pending transaction or transfer (description, amount, material, sender/receiver names) is sent by Telegram to the directors and deputies of ALL companies.
- **backend/src/routes/messages.ts:294-353 (POST /api/messages)** [high] No group-membership or tenant check on groupId: any authenticated user can post into any group by id. The message is stamped with the TARGET group's companyId (:347-348), broadcast through emitToGroup and relayed to every member's Telegram. DMs also do not check that toUserId is in the same company (relayed to the recipient's Telegram at :388).
- **backend/src/routes/ai.ts:379-405 (update_user), backend/src/routes/auth.ts:662-690 (PUT /api/auth/users/:id)** [high] An orinbosar (or the AI acting for one) can change any same-company user's phone, including the owner/direktor's, and can demote a direktor (only promotion TO direktor/dasturchi is blocked). Changing the owner's phone to an attacker-controlled number and logging in by OTP gives an account takeover. There is no isOwner guard and no phone uniqueness pre-check (only the DB unique index error).
- **backend/src/routes/ai.ts:364-375 (delete_user), backend/src/routes/auth.ts:724-733 (DELETE /api/auth/users/:id), backend/src/routes/users.ts:205** [high] Deleting users has no isOwner/direktor protection (users.ts setBlocked does have one). An orinbosar can delete the company owner/direktor. The AI and auth.ts paths do not even prevent self-deletion. There is no audit log on AI deletes.
- **backend/src/middleware/auth.ts:44** [medium] JWT_SECRET falls back to the public literal 'secret' when the env var is missing (only a console warning). Anyone could then forge tokens, including dasturchi tokens, since role comes from the DB but userId is trusted.
- **backend/src/middleware/scope.ts:310-319** [medium] Tenant isolation depends on every route remembering to call scoped(). There is no Mongoose plugin or global hook. With no tenant context (optionalAuth routes, bot handlers, background loops) scoped() returns an UNFILTERED query. Users with null companyId share a 'legacy' pool. Many direct queries skip it (e.g. Group.findById in messages.ts:314/347/358, User.findById in many routes, Attendance.find({userId}) in payroll.ts:41).
- **backend/src/routes/groups.ts:95-118 and :124-146** [medium] memberIds from the request body are not checked to belong to the same company. Users from other companies can be added to a group and then receive its socket events and Telegram relays.
- **backend/src/services/bot.ts (all handlers)** [medium] The bot never checks User.isBlocked (0 occurrences) or subscription/Company status. Blocked users or expired companies keep full Telegram bot functionality (expenses, check-in, approvals) even though requireAuth blocks them on the web.
- **backend/src/routes/auth.ts:337-395 (/login), models/User.ts:55** [medium] The 4-digit Telegram login code is stored in plaintext (telegramVerificationCode) and compared with !== (not constant-time). Rate limits are in-memory (utils/rateLimit.ts), so they reset on a Render restart and are not shared across instances.
- **backend/src/middleware/requireFeature.ts:409-425** [medium] Fails open: companies with no resolvable plan, users without a companyId, or any DB error get full access to paid features (including AI, which has real per-call cost).
- **backend/src/middleware/auth.ts:143-151** [low] Tokens without a jti (issued before sessions existed) skip the revocation check entirely. Session revocation is per-jti only; changing role/phone does not revoke existing sessions.
- **backend/src/routes/payroll.ts:27-60** [low] POST /calculate upserts with $set status:'draft' and netPay recomputed without bonuses/deductions, which overwrites already 'finalized' records (PATCH blocks only 'paid'). Records upserted for a legacy user with companyId undefined will fail the required companyId.
- **backend/src/routes/objects.ts:99 (POST /api/objects/:id/smeta), routes/materials.ts:111 (/send)** [low] No admin role check: any worker in the company (while on shift) can re-upload or overwrite an object's smeta, or send materials.
- **backend/src/routes/attendance.ts:138, utils/tz.ts** [low] The 'late' threshold (09:00) and timezone (UTC+5) are hard-coded. Statuses 'absent' and 'half' are never set automatically by check-in, so AI answers about absences would need to infer them from missing records.

### Gaps
- No Task/assignment model or routes: an assistant cannot create or track tasks ('vazifa') without a new Task model (companyId, objectId, assigneeIds, dueAt, status, createdBy) and routes
- No warehouse/stock module: only Material (per-object needed/sent/remaining) plus Transaction type 'transfer'; 'how much cement is in stock' has no data source
- No timezone field on User or Company; Tashkent UTC+5 is hard-coded (utils/tz.ts). No company work schedule or shift start (late = hour >= 9 hard-coded at routes/attendance.ts:138), so reminders and 'late' logic cannot be configured per company
- Attendance has no objectId, so 'who is at object X today' must be inferred from User.projectIds or GPS
- Object has no workers array; assignment is only User.projectIds (strings) + Object.foremanId; brigade is a free-text User.brigade string; Group is chat-only
- No central RBAC/permission matrix: role checks are copy-pasted inline across routes, so an AI tool layer needs its own explicit per-tool role allow-list mirroring these checks (direktor/orinbosar/isOwner admin; prorab partial in signDocs; workers self-only)
- AI routes are admin-only (requireBoss) and blocked for dasturchi; workers have no AI access, and /api/ai is not in the workGate ALLOW list, so worker voice use while off-shift returns 423
- AI chat uses Groq (GROQ_API_KEY/GROQ_MODEL), not Gemini; Gemini is only used for audio/receipt parsing. A unified Gemini function-calling layer does not exist yet
- AI /execute actions write no audit log (logAudit is not called) and repeat role guards inconsistently with routes/users.ts
- No per-user AI usage/cost tracking persisted (rate limit is in-memory, utils/rateLimit.ts, reset on restart and not shared across instances)
- Telegram bot handlers run without a tenant context (no runWithTenant), so scoped() is a no-op there; any AI voice path via the bot must pass companyId explicitly or wrap in runWithTenant
- Company.status (SUSPENDED) is never enforced, and subscription expiry is checked only at login (issueSession), not per request or in the bot

## telegram-bot

LIBRARY / STARTUP: backend/src/services/bot.ts (3232 lines) uses node-telegram-bot-api (CommonJS require, line 1). It runs at import time: index.ts:53 imports { bot, notifyDeveloper }, so the bot starts whenever the backend starts. It throws if env TELEGRAM_BOT_TOKEN is missing (bot.ts:32-35). Module-level `export const bot` is at bot.ts:43. On import it also calls setChatMenuButton (web_app = SITE_URL, only when SITE_URL is https; :160-163), setMyCommands /start and /res (:1416-1419), starts a 60s setInterval for reminders (:3209-3227) and calls initRegistrationScene(bot) (:3230).

POLLING VS WEBHOOK: if env TELEGRAM_WEBHOOK_URL is set, the bot is constructed with polling:false. setWebHook(`${cleanBase}/api/bot/webhook`, {max_connections:40, allowed_updates:[message, edited_message, callback_query, my_chat_member]}) runs at :94-129. The URL is normalized: trailing "/" and a duplicated path are stripped. If setWebHook fails, it falls back to bot.startPolling() after rewriting bot.options.polling (:119-128). It re-registers the webhook every 5 minutes (:142-144) because a local dev polling instance would make the library delete the webhook. Without the env var it polls with the same allowed_updates (:43-45). The route is index.ts:311-320, `app.post('/api/bot/webhook', express.json(), …bot.processUpdate(req.body); res.sendStatus(200))`, mounted only when TELEGRAM_WEBHOOK_URL is set. It does NOT verify a secret_token or the X-Telegram-Bot-Api-Secret-Token header (grep finds none).

SINGLE-INSTANCE PROTECTION: none beyond webhook mode. There is no lock or leader election. A polling_error handler only logs 409 Conflict and EFATAL (:84-92). All conversational state lives in in-process Maps: chatSessions :216, pendingCheckinLocation :224, pendingBroadcastChoice :245, pendingLabelEdit :626, pendingExpenseEntry/pendingExpenseDrafts :1081/:1090, subscriptionCache :340, lastLiveNudge :3183, and lastReminderKeyIn/Out :2888. The only state that survives a restart is User.lastReminderMsgId.

OUTGOING-MESSAGE SAFETY: bot.sendMessage and bot.editMessageText are monkey-patched (:57-78). On a Telegram "can't parse entities" 400 they retry without parse_mode, stripping HTML tags for HTML mode. Every caller of the exported `bot` gets this behaviour.

ACCOUNT LINKING: models/User.ts field telegramChatId (String, :54). It is not unique and has no index (only indexes at :88-89). User.language is enum 'uz'|'uz-cyrl'|'ru' (:78, default 'uz'). Other fields: telegramVerificationCode/telegramVerificationCodeExpires (:55-56, used for OTP login) and lastReminderMsgId (:80). Linking flow:
- /start (bot.ts:991) finds a user by telegramChatId. If found, it sends startWelcomeBack with keyboardForUser.
- If not found, it sends a request_contact keyboard (sharePhoneBtn).

- /start <token> deep links are left to registrationScene.ts (self-signup; isInRegistration(chatId) guards in the contact and message handlers).
- Mini App login: routes/auth.ts:402 verifyTelegramInitData (HMAC with the bot token) and POST /api/auth/telegram-webapp (:420-431). It logs in only if exactly one user has that telegramChatId.
- OTP login sends a code to telegramChatId (auth.ts:318-327).
Handlers resolve the ERP user everywhere with User.findOne({telegramChatId: chatId.toString()}).

CHECK-IN ("Ishga keldim"):

### Bugs / risks
- **backend/src/index.ts:311-320 and services/bot.ts:104-110** [high] The webhook route accepts any POST and feeds it to bot.processUpdate with no secret_token or X-Telegram-Bot-Api-Secret-Token check, and the URL is predictable (<backend>/api/bot/webhook). An attacker can forge a 'contact' update with from.id == contact.user_id and the victim's phone (bot.ts:1035-1051). That links the attacker's chat to the victim's ERP account, after which Telegram OTP login codes (auth.ts:318-327) go to the attacker, i.e. account takeover. The same forgery works for callback_query (confirm_<txId>, sub_approve_…) using an admin's chatId.

### Bugs / risks
- **backend/src/services/socket.ts:138-143 (relay) and 152-169** [high] Signaling relay forwards the client payload unchanged. 'from'/'fromName' are not overwritten with socket.data.userId, and there is no check that the target 'to' is in the same company. Any authenticated user can send call:offer/end/reject/state to any userId on the platform, spoof the caller identity, and trigger cross-tenant push notifications.
- **backend/src/services/socket.ts:25-27 broadcastPresence** [medium] io.emit('presence', {online: all userIds}) goes to every connected socket of every company: a cross-tenant leak of who is online, plus O(N) fan-out on every connect/disconnect.
- **backend/src/services/socket.ts:83-98** [medium] Socket handshake does not reject isBlocked users, revoked sessions (checkSessionNotRevoked) or maintenance mode, unlike requireAuth (middleware/auth.ts:170-182). A blocked user keeps a live realtime channel and can keep relaying call signaling.
- **backend/src/services/socket.ts:152-162 + frontend/src/app/CallOverlay.tsx:197,258,317** [medium] A push 'Qo'ng'iroq' is sent on EVERY call:offer, including ICE-restart re-offers mid-call (watchMediaFlow) and the group video chat mesh offers a joiner sends to each existing participant. People already in a call get spurious 'someone is calling you' pushes.
- **frontend/src/main.tsx:77-81 + backend/src/services/socket.ts:152-162** [high] Incoming calls effectively reach only users with a live socket. The APK and EXE get no push at all (SW unregistered, no FCM), and on web the push opens '/' without the SDP offer, so the call cannot actually be answered from the notification.
- **frontend/src/app/CallOverlay.tsx:269-299** [medium] For incoming calls the mount effect calls getUserMedia (camera and mic) immediately, before the user presses Accept. The camera/mic turns on and the permission prompt appears while the call is still ringing (privacy/UX).

- **backend/src/routes/messages.ts:342-350** [medium] POST /api/messages with groupId does not verify the sender is a member of that group (only video_invite is checked). Any authenticated user who knows a groupId can post into it, and the post fans out Telegram relays and pushes to all members.

### Gaps
- No persisted or queryable presence: presence is an in-memory Map only. There is no lastSeen on User, no per-device or platform info on sockets (the handshake does not send the X-Client/platform header used by api.ts:9), no foreground/background state, and no multi-instance adapter (no @socket.io/redis-adapter).
- No server-side call state: no Call model, call log, pending-offer store, ring timeout, missed-call record or busy signal. A callee who connects after the offer has no way to fetch it.
- No native push on the apps: there is no FCM. google-services.json is missing, and @capacitor/push-notifications and @capacitor/local-notifications are installed and configured but never used. The SW (and therefore web push) is deliberately unregistered in both Tauri and Capacitor (main.tsx:77-81).
- Android has no incoming-call UI path: no full-screen intent, ConnectionService/Telecom or CallStyle notification, and no wake from a closed app except the 60 s notification poll, which calls never feed because call:offer only does sendPushToUser and never createNotification.
- Tauri: nothing shows or focuses the hidden tray window, or calls requestUserAttention / plugin-notification, on an incoming call. Microphone permission in WebView2 is not handled explicitly; it relies on WebView2's default prompt, with no persisted grant and no custom handling.
- Frontend never subscribes to 'notification:new' socket events (it is emitted by services/notifications.ts but has no listener).
- Push payload for calls has no url/data or requireInteraction, and sw.js has no call-specific actions (Accept/Decline), so tapping it just opens '/'.
- No server API to start a call or 'ring' a user (an AI-initiated call, for example). Ringing exists only as a client-to-client socket relay of a browser-generated SDP offer.

LIVE API FEASIBILITY: @google/genai (the unified SDK; the legacy @google/generative-ai is deprecated) provides ai.live.connect() over WebSocket with function calling, server VAD, input/output transcription and native audio output.

- Constraints:
  1. Live input must be raw 16-bit PCM, 16kHz mono, and output is 24kHz PCM. The current webm/opus MediaRecorder pipeline cannot be reused, so an AudioWorklet capture and a PCM player are needed.
  2. Ephemeral tokens avoid proxying audio through Render.
  3. Uzbek quality and support in the native-audio Live models is not verified and must be tested. A fallback is a half-cascade model with text output plus the existing speechSynthesis TTS.
  4. The current text-JSON action protocol should become real functionDeclarations: send_message, add_user, update_user, delete_user, and read tools such as get_finance_summary or list_users instead of stuffed context. Keep server-side confirmation for destructive tools.
  5. The node-local Node is v24, which is fine for @google/genai (needs Node 18+/20+). backend/package.json has no engines field.
